# pantry client

Generated by `spacepress build`. Typed and dependency-free. Copy this folder into any frontend or
import it by path. Don't edit it: `spacepress build` rewrites it.

A kind's list, get, create, update, delete, paginate and staged steps, an action and a global run
one of the app's WordPress Abilities through core's run route
(`/wp-json/wp-abilities/v1/abilities/<app>/<name>/run`): `client.posts.list()` is `<app>/posts-list`,
`client.actions.rate()` is `<app>/rate`, a global's `get()` is `<app>/global-<name>-get`. The app's own
REST routes under `/wp-json/spacepress/v1/` carry the rest: `count()` and live subscriptions
(`_live`), media, revisions, soft-delete `restore` and `purge`, `auth.me()`, uploads, file downloads,
sign-in, `schema()`, and every call on a kind that has no abilities (a taxonomy). A host serves both.

```ts
import { createClient, SpacePressError } from "./sp/_generated/client/index.ts";

const client = createClient({ url: "https://example.test/wp-json" });

const posts = await client.posts.list({ where: { tags: { has: "news" } }, orderBy: { createdAt: "desc" }, with: { author: true } });
const post = await client.posts.create({ title: "Hello" });
try {
  await client.posts.update(post.id, { title: "" });
} catch (e) {
  if (e instanceof SpacePressError) console.log(e.status, e.code, e.pointer); // 422 invalid_input /title
}
```

## Signing in

The client keeps the session it gets and sends it as `Authorization: Bearer` on
every request. An expired access token is refreshed once and the request retried.
Tokens live in memory, or in `sessionStorage` with `auth: { storage: "session" }`.

```ts
// Redirect to the spacepress-identity screens (PKCE), back on redirectUri.
const client = createClient({ auth: { clientId: "app_...", redirectUri: location.origin + "/callback", storage: "session" } });
await client.auth.signIn();                  // leaves the page
const user = await client.auth.handleCallback(); // on /callback

// Anonymous visitors write as guests, and keep their rows when they sign up.
// With `guests: true`, a write that is refused as unauthenticated starts a guest session and is
// retried; a write a collection allows anonymously (create: "anyone") never needs one, so start the
// session yourself when you want the rows kept. `comments` below stands for a collection of yours
// whose create rule admits guests. The upgrade happens on the spacepress-identity screens, so the client
// needs the same clientId and redirectUri as signIn(); upgrade() redirects and handleCallback()
// finishes it.
const guest = createClient({ auth: { guests: true, clientId: "app_...", redirectUri: location.origin + "/callback" } });
await guest.auth.guest();                                                 // role "guest", tokens held
await guest.comments.create({ postId: 1, name: "A reader", body: "Hi" }); // written by the guest
await guest.auth.upgrade();

await client.auth.signOut();
```

## Live updates

Every read is a `Query`: `await` it for one answer, or subscribe to keep it current.

```ts
const stop = client.posts.list({ where: { status: "published" }, limit: 10 }).subscribe(
  (posts) => render(posts),   // now, and again whenever the result changes
  (error) => report(error),   // a refused read or a network failure; the subscription continues
);
client.posts.count().subscribe((n) => badge(n));
```

All subscriptions of a client travel in one request, which the server answers with "not modified"
or the fresh result, as this client's visitor reads it. Without a host transport the client asks
every 2 to 30 seconds (sooner after a change, never while the tab is hidden); with one registered
through `registerRealtimeTransport`, a change notice asks at once. A write through the same client
refreshes its own subscriptions when it returns. `read.optimistic(update)` shows a write before
the server answers; call `settle()` when it succeeded or `rollback()` when it failed.
See `docs/realtime.md` in the SpacePress repo.

## React

`react.ts`, beside this file, is optional: `createHooks(React)` gives `useQuery(read)` and
`useMutation(write, { optimistic })` for a React frontend that runs outside SpacePress (Next.js,
TanStack Start, an Astro island). It imports no React of its own. SpacePress's own pages don't run
React. See `docs/realtime.md`.

## On a WordPress page

On a page SpacePress renders, `createClient()` with no options reads what the page prints for it
(`<script id="wp-script-module-data-@spacepress/client">`): the site's REST root, the app API's
namespace and, for a signed-in visitor, the REST nonce. Every call is a `fetch` to those routes; the
server checks each ability's input schema, permission and output and answers SpacePress's own errors.
A visitor's page carries no nonce and stays cacheable. `wordpress: false` ignores the page's data; a
client given `url` ignores it too. `wordpress: true` uses the page's nonce even when `fetch`,
`headers` or `auth` is set. These requests don't go through `wp.apiFetch`, so api-fetch middleware a
plugin adds doesn't see them.

A WordPress error (`ability_invalid_input`, `rest_ability_cannot_execute`, `rest_forbidden`,
`rest_cookie_invalid_nonce`, …) reaches you as the same `SpacePressError` as anywhere else:
`invalid_input` 422, `unauthenticated` 401, `forbidden` 403. When the page's nonce has expired while
the page was open, the client gets a new one from WordPress once and sends the request again.

## Other origins, Node, mobile

`url` is the site's REST root: `https://example.test/wp-json`, or `https://example.test/?rest_route=`
when the site has no pretty permalinks (WordPress names its REST root in the
`Link: <…>; rel="https://api.w.org/"` header of every page). The app's API URL
(`https://example.test/wp-json/spacepress/v1`) and the bare site URL work too. A site with another REST
prefix or API namespace: `createClient({ url: "https://example.test/api", api: "acme/v2" })`.

Sign in with an application password (`headers: { Authorization: "Basic " + btoa("user:application
password") }`), a Bearer token from SpacePress Identity, or the sign-in above. `nonce` (a WordPress
REST nonce, `wp_create_nonce('wp_rest')`) uses the visitor's WordPress cookie on the same site.
`auth.session()` hands out the held tokens to forward elsewhere.
