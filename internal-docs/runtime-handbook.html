Purpose and scope

Spacefast Runtime turns uploaded site source into committed versions. It then serves a selected version for each hostname. It also runs Zero server handlers when a compiled route requires one.

Public serving uses local compiled artefacts. It does not call the Spacefast control plane. Management work may call the control plane for key refresh and callbacks.

The runtime understands versions and route pointers. The control plane owns accounts, teams, plans, billing and domain ownership. Those product concepts do not enter the public serving model.

Pre-1.0 boundary. Management API shapes, artefact schemas and storage paths can change without a compatibility layer.

Components and boundaries

The runtime has three execution components. The Rust finalizer and Rust Zero runner are separate programs with different duties.

PHP engine

Request and management plane

Authenticates management calls. Accepts uploads. Resolves hosts and routes. Enforces access rules. Serves files. Dispatches proxies and Zero handlers.

It coordinates finalization but does not compile immutable version artefacts.

Rust finalizer

Publish-time compiler

stattic-runtime-compiler validates staged input and materialises the immutable version tree, indexes, routing artefacts and Zero executable artefacts.

It runs during finalize. It does not handle public HTTP requests.

Rust Zero runner

Request-time JS executor

stattic-zero-runner loads a verified endpoint or run artefact and executes compiled JavaScript in QuickJS.

It runs only for matched Zero work. It does not finalize a version or serve static files.

What runs where

Work Owner When Network position
Management authentication, upload sessions and route updates PHP engine Management request Management hostname only
Version materialisation and immutable artefact creation Rust finalizer Finalize request Local child process; no retained-file network read
Static lookup, redirects, access rules, headers and file responses PHP engine Public request Public hostname; local artefacts
Zero endpoint and run execution Rust Zero runner Matched public or platform request Local child process started by PHP
Routing preparation for Node and CLI consumers Rust core through WASI Build or preview Consumer process; no filesystem-rooted site finalize
Accounts, billing, ownership and publish intent Control plane Product workflow Outside the runtime

Finalizer and Zero are not one component. The finalizer compiles and commits a version. The Zero runner executes a handler from that committed version. PHP is the adapter at both boundaries.

Publication lifecycle

Publication separates mutable upload state from immutable version state. Activation is a route-pointer update, not a copy of the site.

  1. Create. PHP creates a version upload session.
  2. Upload. The client sends whole files, parts, a tar batch or HTTPS fetch requests.
  3. Finalize. PHP invokes the Rust finalizer with a versioned JSON input.
  4. Commit. Rust atomically publishes the immutable version tree.
  5. Activate. PHP points a named route at the committed version and rebuilds route state.

1. Create an upload session

A declared session includes a file manifest. Each upload must match a declared path, size and optional SHA-256 digest. An open session accepts policy-valid paths up to its byte and file-count caps. The runtime derives the final manifest.

A session can name retained files and a reusable version. Before Rust starts, PHP makes retained bytes available in the space-local content-addressed store.

2. Upload bytes

  • A whole-file upload streams bytes to a temporary file and calculates SHA-256.
  • A multipart upload accepts numbered parts. Completion requires a contiguous sequence.
  • A batch upload accepts a bounded tar body for many small files.
  • An HTTPS fetch upload retrieves a source URL under the runtime egress policy.
  • The upload ledger records committed files and staged parts for resume.

The runtime rejects non-canonical paths, traversal, control paths and server execution control files. It also rejects unrelated S3 control operations.

3. Finalize with Rust

PHP verifies that the native compiler exists before it changes version state. It writes a stattic.runtime.finalize.input.v2 file and starts stattic-runtime-compiler finalize. The process receives a private storage root, the space and version identity, session state, serving input, Zero endpoint sources and Zero run sources.

Rust owns every immutable byte and artefact in the version. PHP validates only the result envelope, identity and required container shapes. Rust emits structured error codes for invalid or conflicting input.

4. Commit or restore

When a version already exists, PHP moves it to a recoverable .rust-previous location. Rust stages the replacement and publishes it atomically. A timeout, process failure or invalid result restores the previous tree. Matching retries are idempotent. Conflicting input for an existing version is rejected.

5. Activate

Finalize can include an activation request. A later route update can perform the same pointer change. PHP writes the route pointer, stores serving policy, records a route_updated event and rebuilds the route index.

When the caller supplies a config digest and the route state is unchanged, PHP skips the write, event and index rebuild. When changed-path data is available, the route event carries it for targeted edge-cache purge.

Request and file serving

The public hot path reads compiled PHP and JSON artefacts. It does not parse sf.jsonc, _redirects or _headers.

  1. Classify host. Load an exact or wildcard host shard.
  2. Resolve target. Select a route pointer, immutable version or mount.
  3. Apply rules. Evaluate redirects, access and terminal routing.
  4. Respond. Serve a file, proxy, run Zero or return a platform response.

Path handling

The runtime canonicalises paths before access and routing checks. It percent-decodes once, converts backslashes, removes control characters, resolves dot segments, collapses repeated separators and preserves a meaningful trailing slash.

Compiled serving options cover an index file, clean URLs, directory listing and a fallback. A fallback can set its own status. The lookup artefacts also support nearest custom 404 selection and directory index variants.

File responses

  • Files use compiled content type, size, digest and cache metadata.
  • GET and HEAD share the same lookup and policy path.
  • Byte ranges support local and remotely tiered files.
  • Precompressed representations can be selected when metadata and request headers permit.
  • ETag and conditional request handling use committed file metadata.
  • Protected or synthetic responses do not enter shared caches.
  • Immutable version hosts can receive immutable cache policy.

Terminal outcomes

Outcome Meaning
Static file Serve bytes from the version tree or a verified remote tier locator.
Redirect Return a compiled 3xx response with expanded captures.
Rewrite Resolve a different internal path while keeping the request URL.
Proxy Relay to an allowed external HTTP origin under egress and cache rules.
Zero invocation Send a bounded request envelope to the Rust Zero runner.
Tombstone or platform error Return a compiled response for removed, suspended or pending state.
Not found or undeployed Return a custom or platform 404, or 503 when no deploy route exists.

Routing, redirects and headers

Rust compiles routing convention files during publication. PHP evaluates the resulting artefacts during requests.

_redirects

Rules support exact paths, named parameters, splats and absolute-host sources. They can match query captures and conditions for country, language, cookies and agent requests. A force marker allows a rule to override an existing static file.

Compiled action Source form Result
Redirect 3xx status HTTP redirect
Rewrite Status 200 and path destination Internal path lookup
Proxy Status 200 and absolute URL destination External origin request
Not found Status 404 and path destination Custom 404 body

Compiler diagnostics reject malformed patterns, unsupported status codes, redirect loops and host sources outside the assigned hostname set. Proxy rules retain a serve-time plan gate. A plan change can enable or disable them without republishing.

Proxy rules

Proxy egress resolves and validates the destination. It denies loopback, link-local, private, metadata and Spacefast-internal targets. It pins the connection to validated addresses to resist DNS rebinding.

Shared proxy caching is opt-in with cache=shared. Origin cache headers can still prevent shared storage. Access-protected responses remain private. Request forwarding and response headers pass through allowlists and platform-managed header rules.

_headers

Header blocks can match paths or absolute host-and-path patterns. Each block can set or remove response headers. The compiler canonicalises names and prevents user control of platform-managed headers.

Basic-Auth is not emitted as a response header. Rust lowers it to unified access rules and verifier secrets. Compiler output stores verifier hashes, not the plaintext credentials from the convention file.

Static mounts

A hostname route can mount a committed version from another space at a path prefix. Host-level routing runs before mounted relative routing. The mount then evaluates its own redirects, headers and files against the relative path.

Access, identity and secrets

One ordered policy model covers public access, challenge flows, denial, firewall conditions and Basic Auth.

Rule evaluation

Rules use first-match order. Match fields can include exact or patterned host, path glob, channel, IP ranges, agent, country and a request header. Expired rules do not match. An empty match covers the current scope.

Effects are public allow, authenticated allow, challenge or deny. Authenticated rules compare verified visitor grants with required grant patterns. Acquisition instructions can offer a password or login flow.

Passwords and visitor identity

  • Password and Basic Auth rules resolve named entries from the serving-secret map.
  • Passwords are checked against verifier hashes.
  • Visitor sessions use the shared spacefast_access cookie.
  • A session version can invalidate existing visitor sessions.
  • Grant and subject revocations are checked before a token is accepted.
  • If revocation state cannot be read for a presented token, the request is denied.

Cache and admission rules

Any path covered by a non-public rule is private for cache purposes, including an allowed response. Country-dependent policy also prevents unsafe shared-cache reuse. OPTIONS preflight requests are not challenged.

The runtime applies a per-space concurrency limit to uncacheable work. A route config can override the operational default. Overload returns a bounded failure instead of queuing without limit.

Public content restrictions

Route config can contain a content-type allowlist. The runtime returns 403 when a stored file type matches no allowed exact type or prefix pattern. This check does not depend on the product reason for the restriction.

Zero applications

Zero adds server-side JavaScript, MySQL-backed data and realtime events to a committed version. Static serving remains in PHP. JavaScript execution belongs to the separate Rust Zero runner.

Finalize-time work

A Zero publication can include client and server bundles, public static files, endpoint sources, run sources, a database schema, migrations, variable names, realtime settings and hosted-auth settings.

The finalizer validates endpoint methods and paths. It rejects reserved app paths, private control prefixes, traversal, ambiguous route shapes and non-terminal splats. It asks the Zero runner’s compile interface to produce QuickJS bytecode and generated source. It records digests and capability metadata in endpoint artefacts.

Migrations run at finalize against the provider MySQL database. The migration contract supports table and column creation, indexes, explicit drop operations and explicit rename operations. Incompatible rollback is blocked by the install profile.

Request-time work

  1. Match. PHP resolves method and path against compiled Zero route indexes.
  2. Authorise. PHP applies access policy and selects runtime variables and identity.
  3. Invoke. PHP sends a bounded JSON envelope to the Zero runner.
  4. Execute. Rust verifies the artefact and bytecode, then runs QuickJS.
  5. Return. PHP validates status, headers, body, events and metrics before response.

Endpoint contract

Endpoints can use GET, HEAD, POST, PUT, PATCH, DELETE and OPTIONS. GET also matches HEAD. Routes support named segments and a terminal :splat. More specific compiled matches win.

The invoke envelope contains the method, canonical path, URI, host, origin, query, bounded headers, route parameters, base64 body, space and version identity, schema hash, auth reference and variable reference.

The runner returns a status, filtered headers, text or base64 body, mutation events and timing metrics. PHP removes hop-by-hop and platform-private headers before sending the response.

Capabilities

Each endpoint and run declares access to database, outbound fetch, auth, environment variables, realtime and logging. The runner generates its JavaScript prelude from that capability set. Missing capability is not treated as permission.

Database calls use bound parameters and a provider-scoped connection. Query, execute, transaction begin, commit and rollback paths return structured errors and metrics. Schema metadata governs database use.

Platform routes

Route Purpose
/__spacefast/zero/config Client-safe runtime configuration.
/__spacefast/zero/realtime Realtime configuration and replay path where enabled.
/__spacefast/zero/inspect Application and install metadata under the configured inspect policy.
/__spacefast/zero/db Database inspection and dump surface under runtime checks.
/__spacefast/zero/logs Structured execution log access.
/__spacefast/zero/run Invoke a compiled run handler by identifier.
/__spacefast/zero/auth/wpcom/start Start configured WordPress.com hosted authentication.
/__spacefast/zero/auth/sign-out End the shared hosted-auth session.

Realtime and activation

Production modes use central realtime or Spacefast Cast. Local development can use a foreground CLI WebSocket. Committed mutations produce events with a request ID, changed tables and queries, schema hash and commit time.

A Zero route can exist in an activating state. PHP returns an activation response rather than running incomplete code. This prevents traffic from reaching an endpoint before its executable graph is ready.

The Zero runner does not replace PHP. PHP still resolves the host, applies access and route rules, builds the invoke envelope and validates the runner response.

Content compilation

Content conversion happens during finalization. The serving path reads the generated files and metadata.

Core configuration

sf.jsonc can set index, fallback, clean URLs, listing, metadata, templates, theme, Markdown negotiation and HTML injection. Rust parses JSONC, resolves effective configuration and emits diagnostics through versioned preparation interfaces.

Experimental Gutenberg pipeline

Experimental and hidden. This pipeline runs only when experimental_gutenberg is strictly true. Its hooks, page shapes, output paths and diagnostics can change. When the flag is off, finalization stays byte-for-byte aligned with the non-pipeline path.

When enabled, the pipeline can:

  • Parse Markdown front matter and Markdown documents.
  • Parse Gutenberg block documents with the native Rust token walker.
  • Render supported blocks to HTML.
  • Exclude draft pages.
  • Apply cascading _layout.html documents.
  • Compile selected theme.json settings to generated CSS.
  • Inject metadata and configured head, body and noscript snippets.

The passes use the file tree and compiled config. They do not use network, clock or random input. Invalid content is skipped with a diagnostic rather than aborting finalize.

Management and data movement

Management routes exist only on the configured management hostname. Public hosts reject management paths before token parsing.

Authentication lanes

Lane Audience Scope
Management stattic-runtime-management Runtime instance, action, operation and route resource. Single-use JTI.
Upload stattic-runtime-upload Upload session, space, version and session mode.
File fetch stattic-runtime-file-fetch Short-lived read scope for a path, digest or scan manifest.

Management JWTs use Ed25519 keys from local, inline or fetched JWKS. Tokens carry exp, nbf, jti, action and resource claims. Mutation handlers run only after method, route, token and scope checks.

Management surfaces

  • State summary and callback event drain.
  • Engine job create, tick and read.
  • Version create, upload status, finalize and delete.
  • Route, hostname intent, tombstone and retention-policy updates.
  • Grant and subject revocation updates.
  • Space repair and delete.
  • Chunked export and import.
  • Transfer bundle, commit and abort.
  • Read-only scan manifest, file-by-path and file-by-hash fetch.
  • Access-event read.

Export and import

Export and import are stepped jobs. A step advances bounded work and returns progress. The archive root is spacefast_export_v1. It contains an identity document, selected committed versions and their artefacts. It can also carry the space access policy.

An import validates the archive layout and materialises versions. A caller can map source version IDs to new IDs. Rust rebinds the imported Zero executable graph to the target space and recompiles finalized Zero source when required.

Exports do not include account ownership, billing or domain records. A downloaded export plus the engine can serve the site in a self-hosted installation.

Transfer

The transfer API prepares a portable bundle, commits received state, or aborts staged transfer work. Commit stays separate from bundle preparation so a partial transfer does not become active.

Storage, tiering and retention

Local immutable version trees use a per-space content-addressed blob store. Optional tiering can move eligible representations to S3-compatible storage.

Local layout

.stattic/storage/
  runtime/
    uploads/                 mutable upload sessions
    jwks.json                fetched key cache
    jti/                     replay markers
    callbacks/               pending callback records
    journal.jsonl            operational event journal
    jobs/                    durable engine jobs
  spaces/<spaceId>/
    blobs/<prefix>/<sha>     per-space content-addressed bytes
    versions/<versionId>/    committed files and compiled artefacts
    routes/<routeName>.json  mutable route pointer
    policy.json              unified access policy
    policy-secrets.json      verifier and serving-secret values
  routes/
    current.php              active generation pointer
    generations/             compiled host shards

Deduplication

Finalization stores content by SHA-256 and links version files to the space-local blob. Retained files can be recovered from an existing version, the local blob store or a configured cold bucket. Blob ownership stays inside one space.

Cold tier

A demotion job handles each file representation, including identity, Brotli and gzip entries. Its order is: upload, verify, rewrite the file shard with a remote locator, wait through a reader grace period, unlink the local hardlink, then emit the callback.

A public request can stream a remote representation. Tier fetches use a per-box concurrency cap and a per-bucket circuit breaker. Failure records enter the journal and a bounded event spool. Promotion restores verified local bytes and updates metadata.

Retention and garbage collection

The control plane sends a set of prunable version IDs. A bulk housekeeping job checks that no live route points at a version before removing its tree.

Local blob collection scans for old, regular files with one remaining hardlink. It acquires the owning space write lock before unlink. Contended or incomplete scans do not advance the completion marker. A successful removal writes a local_blob_gc journal event.

Hostnames and route state

Hostname intent compiles into generation-stamped route shards. One current pointer activates a complete generation.

Hostname classes

  • Production hostnames follow a named route pointer.
  • Immutable version hostnames point at one retained version.
  • Noindex production hostnames receive search-index restrictions.
  • Canonical host redirects send one hostname to a configured URL.
  • Wildcard host entries use a compiled wildcard shard.
  • Static mounts attach a target version below a host path prefix.

The intent for immutable version hosts is a complete retained-version map. A route update therefore does not orphan an older version URL.

Generated route state

Exact hosts live in hash-prefix shards. Wildcards live in their own artefact. Each shard declares the generation that built it. A schema or generation mismatch returns a runtime invariant error.

Repair rebuilds route indexes from durable space state. Tombstone updates can replace, add or remove hostnames and can select status 402, 404 or 451 based on the supplied category.

Jobs, events and concurrency

Runtime management uses durable files, named lanes and bounded ticks. Public requests do not become the job queue.

Engine jobs

Job creation uses an idempotency key. Repeating the same key returns the existing active job. Jobs store their type, payload, cursor, progress, operation identity and retry state.

A tick claims work from a lane, advances a bounded step and records completion, retry, cancellation or dead-letter state. Job callbacks reuse the management event mechanism. Housekeeping covers tier work, pruning, disk reports and local blob collection.

Events and journal

Mutations append operational events to .stattic/storage/runtime/journal.jsonl. Callback delivery has a pending store and drain route. Operation IDs connect runtime results to control-plane work.

A route update event can carry affected hosts, the previous version and up to the contract limit of changed request paths. If no reliable diff exists, downstream purge logic can use a host-wide fallback.

Lock scope

Lock Protects Reason
Site write lock Site-wide mutable state and generation changes Prevents conflicting global rewrites.
Space write lock One space’s versions, blobs, policy and revocations Allows unrelated spaces to proceed.
Upload ledger lock One upload session Keeps part and file accounting consistent.
Job lane lock One engine work lane Prevents duplicate claims without taking the site lock.
Admission counter Uncacheable and tier-fetch concurrency Bounds public request work.

Security boundaries

The runtime treats generated artefacts, private storage and process boundaries as explicit trust boundaries. Unknown or malformed control data fails closed.

Upload and serving

  • User PHP-like files remain inert bytes. The runtime never executes uploaded PHP.
  • Upload and serve policy blocks .htaccess, .user.ini, private storage and engine paths, and __spacefast control names.
  • Direct web access to .stattic/** must also be denied by the web server.
  • Archive import checks layout and guards against unsafe expansion and active PHP.

Authentication

  • Management and upload surfaces are bound to one management hostname.
  • JWT audience, runtime instance, action and resource scope must match.
  • Management JTI markers are single use.
  • A replay-cache storage failure returns 503. It is not reported as a replay.
  • Visitor token verification denies access when revocation state is unavailable.

Native processes

  • The finalizer fails with 503 when its binary or process interface is unavailable.
  • The finalizer receives a canonical private root and versioned input format.
  • The Zero runner receives a bounded stdin envelope.
  • Zero artefact paths stay below the committed version root.
  • Bytecode digests and endpoint identity are checked before execution.
  • Capability declarations control which JavaScript APIs the generated prelude exposes.

Network egress

Proxy and fetch paths validate schemes, hosts and resolved addresses. Connection pinning prevents a later DNS answer from changing a validated public target into an internal one. Response headers do not get authority to override platform safety policy.

Artefact invariants

Compiled files carry format, schema and kind metadata. Missing or incompatible route, serving or Zero artefacts produce a runtime invariant error. The runtime does not guess an action for an unknown artefact shape.

Rust, WASI and preview interfaces

One Rust core supplies native finalization and pure preparation operations. The execution target determines which functions are available.

Native compiler

stattic-runtime-compiler exposes:

  • build for compiler input that produces artefacts outside site commit.
  • finalize for versioned compile or filesystem-rooted site finalization.
  • rebind-import for Zero graph rebinding after import.
  • self-test for installed binary verification.
  • --dry-run for full v2 pipeline execution without publishing the staged version.

WASI module

stattic-runtime-wasi exports JSON operations for routing compilation and preparation. Node consumers load the module through a WASI Preview 1 host. Preparation includes config parsing, analysis, strict config, effective config, theme work, routing policy, HTML transform, page compile and bcrypt verification.

Filesystem-rooted site finalization is native-only. The WASI sf_finalize export stops with an unsupported error because Zero endpoint compilation needs the native QuickJS runner.

Browser and CLI preparation

Browser-safe preparation does not import the Node WASI host. Node, CLI and server build paths can call the embedded or packaged WASI module. This keeps route diagnostics and config preparation aligned with native Rust without giving a browser filesystem access.

Zero runner commands

stattic-zero-runner exposes:

  • stdio invocation for request and run envelopes;
  • compile for endpoint source, generated source and QuickJS bytecode;
  • migrate for a committed version’s migration plan;
  • --self-test for QuickJS and ABI verification.

Recovery and troubleshooting

Start with the failing boundary: host routing, management authentication, upload state, finalization, Zero execution or storage tier.

Signal Meaning Action
runtime_api_not_found The request did not reach a management route on the management host. Check the Host header and configured management hostname.
runtime_instance_mismatch The token names another runtime instance. Mint a token for this instance. Do not reuse another runtime’s token.
runtime_jwks_key_missing or fetch failure The runtime cannot obtain the signing key. Check local or inline JWKS, or the configured API base URL.
upload_not_found The session expired, was finalized or does not exist. Create a new version session. Query upload status before retrying files.
finalize_unavailable The native compiler is missing, not executable or cannot start. Check the engine bundle, executable bit and process functions.
runtime_finalizer_timeout The finalizer exceeded its process deadline. Inspect input size and host resources. The previous version is restored.
version_existing_mismatch A retry conflicts with the committed identity or input. Use a new version ID for different content.
Public 503 undeployed No active route generation maps the hostname to a version. Finalize a version and update its route or hostname intent.
artifact-schema-mismatch Compiled state does not match the installed engine schema. Restore a matching engine or rebuild route and version artefacts.
zero_* runner error Zero route, envelope, bytecode, capability, database or handler work failed. Use the exact error code, inspect endpoint artefacts and review Zero metrics.
Tier fetch failure Remote bytes could not be read or the bucket breaker is open. Check bucket config and journal events. Promote the version when needed.

Operational checks

  1. Call the public-safe health endpoint and record engine revision and site state.
  2. Call management state with a correctly scoped token.
  3. Confirm the hostname exists in the active route generation.
  4. Confirm the route pointer names a committed version.
  5. Inspect the upload session before repeating upload work.
  6. Inspect runtime/journal.jsonl and pending callbacks.
  7. Read an engine job by ID before creating replacement work.
  8. Use space repair after manual storage intervention or route-index drift.

Recovery boundaries

  • A failed native finalize restores the prior immutable version when available.
  • A failed finalize does not switch a route pointer.
  • A transfer bundle does not activate until commit.
  • A demotion callback occurs only after remote verification, metadata rewrite and local unlink.
  • A partial garbage-collection scan does not mark the scan complete.
  • A missing policy, entitlement or revocation dependency does not grant extra access.

Glossary

Activation
A route-pointer update that makes a committed version serve for selected hosts.
Artefact
Compiled, versioned runtime data used without reparsing source conventions.
Finalizer
The Rust stattic-runtime-compiler process that materialises immutable version files and serving artefacts.
Management hostname
The only hostname allowed to expose runtime management and upload APIs.
Route pointer
A named mutable record that selects one committed version and serving config.
Route generation
An atomically selected set of exact and wildcard hostname shards.
Space
The runtime storage and policy boundary that owns versions, routes and blobs.
Version
An immutable committed file tree and its compiled serving artefacts.
Zero
The application runtime mode for compiled JavaScript handlers, MySQL data and realtime events.
Zero runner
The separate Rust stattic-zero-runner process that executes a verified Zero endpoint or run handler in QuickJS.
