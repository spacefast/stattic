Architecture decision and delivery plan

Stattic Builder builds. Stattic Runtime admits and serves.

Make the CLI the normal build environment, keep one Rust compilation authority, and make the PHP Runtime fully useful without a Rust finalizer. Spacefast uses the same bundle contract for direct publishes, Git builds, dashboard uploads, imports, and self-hosting.

25 July 2026 · Status: adversarially reviewed and revised · Scope: Builder, CLI, Runtime, control plane, Zero, and wp.cloud delivery

Decision

The canonical publish artifact is a verified Stattic deployment bundle, not an upload session waiting to be compiled.

The Rust finalizer is assumed merged and is the starting point for this work. We factor its compilation authority into Stattic Builder, run it from the CLI and Spacefast Builder hosts, and replace runtime finalization with a compiler-free admission operation.

1. Merged baseline

Planning rule: the Rust finalizer has landed. It is not a prerequisite, option, experiment, or future merge in this plan. Every change below is made on top of its one-parser, one-finalizer ownership boundary.

The merged baseline already provides the hard parts worth preserving:

  • Rust owns upload materialization, Markdown, Gutenberg, themes, layouts, routing artifacts, HTML decoration, and Zero compilation.
  • The CLI and control plane already ship the same Rust core as an embedded WASI artifact. Standalone CLI smoke tests exercise it.
  • PHP authenticates management calls, owns storage and atomic activation, invokes the native finalizer, and serves the resulting immutable version.
  • Version finalization already has durable control-plane receipts, retry ownership, runtime state reconciliation, activation CAS, and changed-path purge semantics.
  • Runtime import already validates archive structure and can install static compiled versions without invoking the native binary. Zero import is the remaining target-rebind exception.

The cutover moves where compilation runs. It must not reimplement the finalizer in TypeScript or PHP, weaken durable publication, or create a second artifact language.

3.2 One core, multiple hosts

Extract the merged finalizer into a host-independent Rust core with explicit source and artifact interfaces. The current WASI surface is not a full site builder: it exposes in-memory preparation operations and deliberately rejects filesystem-rooted site finalization. Phase 1 therefore adds one specific missing host contract rather than pretending the existing artifact is sufficient.

  • WASI host: a full static-site build_bundle operation with sandboxed preopened source/output directories, embedded in npm and standalone CLI releases. It has no network access and emits target-neutral Zero input only.
  • Spacefast host: the same Rust core exposes a separate bind_bundle ABI operation through allowlisted WASI bytes or a thin native adapter in an ephemeral tenant-isolated sandbox. It is never loaded inside the control-plane or queue-worker process.
  • Native developer host: deterministic fixture runs, benchmarks, and debugging.

The filesystem-rooted finalizer becomes one host adapter rather than the architecture. Protocol metadata and golden vectors prove all hosts use the same Builder ABI. Release provenance records the SHA-256 of the actual WASI bytes; a claimed semantic version or Git revision is not sufficient. Developer overrides are explicitly untrusted and cannot claim Spacefast Builder provenance.

3.3 Two-stage output

  1. Portable content pack: locally compiled pages, blocks, theme output, normalized routes, headers, static files, and non-target-bound Zero inputs.
  2. Target binding pack: Spacefast policy, platform injection, channel variants, target identity, opaque secret-handle references, and final Zero binding.

A deployment bundle combines both digests. Most work is local; sensitive or target-specific work stays trusted. Builder is secret-blind in both stages: target binding receives opaque secret handles and monotonic handle revisions, never secret values or deterministic value digests. A completely portable static site has an empty binding pack and can be admitted by any compatible self-hosted Runtime.

3.4 Dependency classes, not “config-only” guesses

Builder emits a dependency receipt that classifies every input:

  • Content inputs: source bytes, Markdown/block/theme semantics, redirects, headers, and compile-time public variables. Spacefast plan policy never changes portable artifact identity.
  • Binding inputs: target identity, placement epoch, Runtime instance, target-bound Zero graph, platform injection, and path-level replacement blobs.
  • Activation inputs: hostnames, channel ownership, mutable cloud policy, secret-handle revisions, and expected serving generation.

A binding pack is a path-level patch manifest anchored to one contentDigest. It may replace named blobs but cannot contain semantic source nodes or invoke Markdown, Gutenberg, theme, or routing parsers. Any change to a content input rebuilds the content pack.

Introduce stattic.bundle.v1. Do not overload spacefast_export_v1: exports are multi-version migration archives with route history, while bundles are one immutable build result.

4.4 Data, not executable PHP

The public bundle contract is language-neutral data. It must not require arbitrary PHP from an uploaded archive. During admission, trusted Runtime code may emit optimized PHP array caches from validated schemas. That is deterministic materialization, not semantic compilation: it never parses source, renders Markdown, or changes routing meaning.

Builder emits the complete canonical Runtime IR. PHP may only perform schema-preserving serialization or indexing whose decoded value is hash-equivalent to that IR. It cannot normalize routes, apply defaults, lower themes, or reinterpret headers. Cross-language serving vectors must prove that Builder IR and served behavior agree. If this isomorphism cannot be proven, Runtime serves the validated neutral tables directly.

4.5 Verification

The Runtime verifies every claim rather than trusting the descriptor:

  • ZIP/path safety, decompressed size, entry count, and compression-ratio bounds.
  • Every file digest, aggregate manifest digest, and artifact graph reference.
  • Builder ABI and Runtime ABI compatibility.
  • Required artifact completeness for the declared profile.
  • Target identity, binding digest, expiry, and signature when a binding is present.
  • No source-only nodes or unresolved target placeholders when serverBuild is false.

4.6 Identity is separate from authorization

contentDigest, bindingDigest, and deploymentDigest cover canonical artifact identity only. Nonces, expiry, signatures, upload authorization, and operation IDs live in a separate admission envelope so identical artifacts remain deduplicable.

Execution provenance is separate too. A signed provenance envelope records hostKind, actual Builder artifact SHA-256, release revision, and security epoch, but is excluded from content/deployment identity. Static CLI and hosted builds can therefore prove different trusted hosts while producing one canonical artifact digest.

  • Expiry is enforced before first acceptance.
  • An exact accepted receipt may replay after envelope expiry with a fresh management JWT.
  • The same Space/version/receipt with a different deployment digest is a hard conflict.
  • Admission authorization binds the exact deployment digest, profile, target Space/version, and operation.

4.7 Strict parser budgets

The new bundle reader reuses lessons from import safety, not its legacy PHP parsing lane. It rejects duplicate raw or normalized paths, Unicode/case collisions, links, devices, unsupported compression, unknown records, and any non-bijective manifest/blob graph. It enforces per-entry and aggregate compressed bytes, expanded bytes, file count, JSON depth, collection cardinality, CPU, and staging-disk budgets. Bundle-supplied PHP is never evaluated or included.

5. Native Spacefast integration

Spacefast should not bolt a bundle endpoint beside the existing publish lifecycle. The bundle becomes the lifecycle's artifact, while existing authorization, durable operations, route CAS, provider locks, health probes, and reconciliation remain authoritative.

5.1 Direct CLI publish

  1. CLI completes the optional framework/app build, then invokes embedded Stattic Builder to create the target-neutral portable content pack offline. A failed local build creates no Space or cloud resource.
  2. CLI resolves or creates the Space and requests a short-lived build context. The response contains Runtime ABI, Builder ABI, plan policy, public platform inputs, target-binding nonce, and input generations—never secrets.
  3. CLI uploads missing bundle blobs under a publish-attempt/artifact-object identity, not a version. Client digests are hints until verified; a known verified object may be reused.
  4. Control plane universally consumes the build context and freezes an artifact-acceptance receipt, fencing authorization owner, all input generations, Builder allowlist epoch, placement, expiry, and verified artifact identity.
  5. It then transactionally compares the complete desired artifact/activation identity with exact observed Runtime state. A true no-op returns the current version and mints no version. Otherwise it allocates the version and binds the verified artifact to it.
  6. If binding is needed, the control plane freezes a durable binding-build receipt before invoking the trusted Builder host. The verified binding output advances the operation to the next phase; retries never rebuild under a newer Builder or context.
  7. Control plane freezes a separate admission receipt only after the full deployment digest exists. Runtime admission installs the version but does not imply channel activation.
  8. Control plane freezes an activation receipt with an expected Runtime serving generation. Runtime activates by generation CAS, then the control plane commits ready/channel state and verifies exact public serving.

5.2 API vocabulary

Stop using “finalize” for both compilation and business completion. Preserve Spacefast's agent-friendly convenience publish action and keep granular APIs for resumable CLI work:

Surface Action Semantics
CLI sf build, sf publish Build locally, then publish the resulting artifact.
Spacefast API POST /spaces/:id/build-context Freeze non-secret target inputs and return their digests.
Spacefast API POST /spaces/:id/versions Create a version intent around a source or prebuilt bundle.
Spacefast API POST /v1/publish Public convenience action: accepts source/archive for trusted remote build or application/vnd.stattic.bundle for direct admission; returns the existing Space/version/claim/operation receipt shape.
Runtime API POST /spaces/:id/versions/:id/admit Verify and atomically install an already-built deployment bundle.
Runtime API PUT /spaces/:id/routes/:route Activate one immutable serving generation with expected-generation CAS.

This is a pre-launch cutover: delete the old Runtime finalize route and its obsolete contracts/tests once all publishers use admission. Do not keep a shadow compatibility lane.

5.3 Durable state

Make artifact provenance first-class rather than burying it in source metadata:

  • build_mode: local, spacefast, or import.
  • builder_abi and builder_revision.
  • content_digest, binding_digest, and deployment_digest.
  • build_context_digest and optional expiry.
  • A version-delivery phase ledger with monotonic epoch and exact receipt IDs.

Do not collapse bind, admit, activate, and public proof behind one opaque mutation. Each external effect has a frozen input and a verified output:

Phase Frozen before effect Observed output
artifact_acceptance Verified artifact, authorization owner, all context generations, Builder allowlist epoch, placement, expiry. Accepted artifact identity or exact no-op result before version allocation.
binding_build Content digest, build-context digest, Builder byte digest, placement epoch, opaque secret handles and revisions. Verified binding and deployment digests.
admission Deployment digest, Runtime instance, ABI/security epoch, exact operation ID. Runtime admission receipt with immutable version identity.
runtime_secret_stage Version, deployment digest, Runtime/placement epoch, encrypted payload digest, handle revisions. Idempotent Runtime secret-set receipt; staged values remain unreachable to serving requests.
zero_migration Migration-plan digest, target database identity, secret-set receipt, Runtime/placement epoch. Exact per-migration receipts and terminal schema proof.
activation Ready projection, route config, policy/secret-handle revisions, expected serving generation. Runtime activation receipt and new serving generation.
public_proof Expected host, version, deployment digest, Runtime revision. Observed HTTP/version headers and terminal domain success.

The build context is stored server-side with one-time nonce, authorization owner, config/policy/variable generations, placement generation, Builder allowlist epoch, and expiry. It is consumed for every publish when artifact acceptance freezes, whether or not binding is needed. Expiry blocks the first effect, but cannot strand an exact already-frozen retry.

Every transition CASes (operation_id, phase, epoch, delivery_claim_id) in one Postgres transaction before effect dispatch. Builder and Runtime requests bind the resulting phase receipt ID and epoch. A stale worker may replay an already accepted exact receipt, but cannot create or dispatch the next phase.

5.5 Config-only and dedupe

“Config-only” is user intent, not a cache boundary. Builder's dependency receipt decides whether the change invalidates content, binding, or activation. Serve-only and binding-only changes reuse the content pack; theme, routes, headers, template, public compile-time variable, or entitlement changes rebuild it. A no-op is allowed only when complete desired deployment and activation identity equals exact observed Runtime identity.

Unknown artifacts are verified under publish-attempt identity before this decision. Only a non-no-op allocates a version row or version number.

5.6 Runtime generation transaction

A write lock prevents concurrent mutation but does not make several files crash-atomic. Activation therefore writes one immutable record containing version, deployment digest, route config, policy, secret-handle references, hostname intent, changed paths, and activation epoch. Runtime builds every derived projection from that record and atomically flips one serving-generation pointer last.

  • Runtime rejects a stale expected serving generation or route digest.
  • Exact receipt replay returns the same stored activation result.
  • Recovery reconstructs projections from the immutable activation record.
  • Crash injection after every subwrite must prove either the old or new generation serves, never a mixture.

5.7 Observed Runtime truth

Authenticated Runtime state—not public health—reports:

  • Admitted (versionId, deploymentDigest, runtimeAbi, admissionReceiptId).
  • Active (route, versionId, deploymentDigest, routeConfigDigest, bindingDigest, activationEpoch).
  • Runtime instance/revision, release-manifest digest, security epoch, and serving-generation ID.

Postgres owns desired/domain truth; Runtime reports observed serving truth. Terminal success is their exact join. A matching version ID alone is insufficient for forward completion.

5.8 Multi-version import

A Spacefast export remains an orchestration container holding portable version bundles and channel/history topology. Import freezes the complete source→target version map before the first admission, then gives every target version its own durable phase receipts. Partial completion is resumable, not presented as an all-or-nothing rollback. Channels move only after the required version set is observed admitted. Every destination binding/signature is regenerated; same version/same deployment digest replays, while same version/different digest conflicts.

8. Zero and target binding

Do not overstate the PHP-only promise. A prebuilt static site needs no Rust process on the Runtime. A Zero site still needs the current Rust Zero executor unless Zero adopts a different execution substrate. That executor is not the finalizer and must have a separate capability bit.

Today, imported Zero artifacts are rebound on the destination Runtime. Move that work into the trusted Builder host:

  1. Control plane freezes target Space ID, exact Runtime instance and placement epoch, Runtime ABI/security epoch, Zero isolation mode, capabilities, opaque resource handles, and secret-handle revisions.
  2. The trusted host invokes bind_bundle on the same Rust core to compile the target-bound Zero graph and emit a binding digest.
  3. Spacefast signs the target binding envelope. Builder never receives secret values.
  4. Runtime verifies target identity and signature, then installs the graph without rebinding.

A portable bundle containing Zero source but no target binding is incomplete. A serve-only Runtime returns 422 target_binding_required before staging any version. It never invokes Builder or installs source-space executable artifacts.

8.1 Secret and callback contract

Secrets are not compile-time variables. Static templates cannot consume secret-scoped values; use public build variables for static substitution or Zero for runtime secret use. The bundle and externally readable build/admission receipts contain only opaque secret-handle IDs and monotonic revisions. If the control plane needs secret change detection, it keeps a keyed HMAC or encrypted fingerprint server-side only; no deterministic unkeyed secret digest crosses an API or artifact boundary.

  • Control plane stores encrypted, version-scoped secret bindings outside the bundle and sends them through a separate authenticated Runtime configuration operation.
  • The durable runtime_secret_stage phase binds encrypted payload digest, placement epoch, and exact handle revisions; response loss replays the same Runtime secret-set receipt.
  • Staged secrets remain unreachable to serving requests. Only the authenticated migration executor can use the exact staged set before activation; activation later pins that same secret-set receipt and its handle revisions to the serving generation.
  • Runtime injects values into the Zero process at execution time; migration execution uses the same authenticated handle resolution.
  • Callback credentials are minted after admission and never become bundle content.
  • Rotation or revocation changes activation identity; Runtime relocation always produces a new target binding.

8.2 Zero migration phase

Zero migrations are an irreversible external database effect and cannot hide inside admission or activation. After secret staging, the durable zero_migration phase freezes migration-plan digest, target database identity, exact secret-set receipt, Runtime/placement epoch, operation epoch, and delivery claim. Each migration has an idempotency key and durable receipt; response loss probes exact schema or migration-ledger state and forward-completes rather than rerunning blindly. Activation requires successful exact migration proof, so new code never serves before its schema.

9. Security and trust boundaries

Threat Required control
Caller labels source as prebuilt Artifact graph validation; mode is derived, not trusted.
ZIP traversal/bomb Existing import caps generalized into one admission reader; bounded staging.
Malicious executable PHP Language-neutral bundle; Runtime emits its own caches from validated data.
Bundle tampering Per-blob hashes, domain-separated aggregate digests, signed Spacefast binding.
Replay to another Space Target Space, version, Runtime ABI, nonce, and expiry covered by binding signature.
Stale policy or platform injection Server-stored context generations consumed atomically when artifact acceptance freezes.
Secret exfiltration Builder is secret-blind; no secret values in context, artifact, provenance, diagnostics, receipts, caches, staging, stdout, or logs.
Partial install Verify in unreachable staging, fsync where supported, atomic rename, then pointer CAS.
Compiler fallback on Runtime Serve-only package excludes the binary; admission code has no invocation dependency.

9.1 Three independent trust layers

  • Content integrity: canonical manifests and digests prove exact bytes.
  • Publisher authorization: management JWT binds deployment digest, profile, target, version, and operation.
  • Builder provenance: optional dedicated artifact signature proves an allowlisted Builder byte digest and security epoch.

The artifact-signing key is separate from visitor and management JWT keys and has kid, rotation, revocation, and minimum-security-epoch policy. Self-hosted Runtime either trusts configured publisher keys or records an authenticated operator upload as unverified; there is no unauthenticated unsigned admission mode.

9.2 Runtime release authenticity

Runtime distribution needs stronger authenticity than the current package. Every serve-only or serve-zero release is a separately signed artifact with an offline release-key envelope covering profile, security epoch, revision, complete file list, per-file SHA-256, executable modes, and capability manifest. The installer pins the trust root, performs bounded extraction into an immutable release directory, rejects links/devices/duplicate or non-canonical paths before writing, verifies everything, then atomically switches the active release pointer. Query-string installer credentials are removed in favor of a header or CLI-only channel.

9.3 Downgrade and revocation

ABI compatibility is necessary but insufficient. Spacefast pins minimum Builder, bundle, and Runtime security epochs; Builder byte digests and Runtime release digests are allowlisted, and emergency revoked-digest lists fail closed before first admission.

9.4 Remote Builder isolation

Tenant-controlled source never executes in a control-plane or durable queue-worker process. Every hosted build runs in an ephemeral unprivileged sandbox with a read-only Builder runtime, explicit source/output mounts, no ambient environment, no network, and CPU, wall-time, memory, PID, output, and filesystem quotas. Writable caches are isolated per build or content-addressed and verified before reuse. WASI traps, native crashes, panics, and quota kills become bounded build failures rather than worker deaths.

10. Cutover sequence

Each phase ends in a shippable invariant. There is one migration on the implementation branch; schema changes should be folded into it until the PR lands.

Phase 1 — Graduate the authoring and host contracts

  • Rename the public product boundary to Stattic Builder and Stattic Runtime.
  • Make Markdown a public default and specify routes, frontmatter, layouts, collisions, drafts, watch, and preview.
  • Publish the versioned Gutenberg/core-block and theme compatibility matrix.
  • Add the full static build_bundle WASI host with sandboxed preopens; keep target-bound Zero out of it.
  • Add trusted-host bind_bundle and the non-admissible portable-zero-input profile.
  • Generate one Builder ABI contract for Rust, TypeScript, and PHP consumers.
  • Define stattic.bundle.v1, profiles, digest rules, and canonical ordering.
  • Add cross-host golden vectors for Markdown, Gutenberg, themes, routing, and Zero inputs.

Phase 2 — Make Builder produce a real bundle

  • Factor filesystem writes out of the merged Rust finalizer core.
  • Add deterministic content-pack output and incremental dependency metadata.
  • Replace the CLI's compiler dry-run while retaining the existing app-build → artifact-compile meaning of sf build.
  • Ship the Builder WASI artifact in npm and every standalone target.
  • Make sf dev watch and preview through the same Builder dependency graph.

Phase 3 — Add compiler-free Runtime admission

  • Build a strict language-neutral bundle reader; do not inherit legacy PHP token/eval behavior.
  • Add staging, verification, cache materialization, and immutable admission commit.
  • Add immutable activation records, expected-generation CAS, and one serving-generation pointer.
  • Add signed profile-specific Runtime releases plus informational health and authoritative authenticated state.

11. Acceptance gates

  • On a Runtime package with both the finalizer binary and its environment overrides absent, sf publish successfully publishes Markdown, Gutenberg, a compatible block theme, redirects, headers, and static assets.
  • A test trap fails if bundle admission calls proc_open, Builder, or a compiler binary.
  • Two builds from the same source, Builder revision, and context produce identical content and deployment digests on macOS and Linux.
  • npm and every standalone CLI target build a real Markdown + Gutenberg + theme .stattic bundle without Cargo, a native compiler, or environment overrides.
  • A first anonymous publish builds portable content before creating the Space; a local failure leaves no orphan cloud resource.
  • CLI WASI and trusted hosted Builder hosts produce one canonical artifact digest while retaining distinct signed execution-provenance envelopes.
  • Bundle destinations inside the selected input tree are rejected, and repeated builds cannot include a previous .stattic artifact.
  • Tampered blobs, missing artifacts, stale contexts, target mismatches, and unsupported ABIs fail before immutable install or pointer mutation.
  • Secret-bearing templates and Zero environments leave no secret values in CLI build context, bundles, Postgres receipts, Runtime staging, cache files, logs, diagnostics, Builder stdout/stderr, exceptions, or version API output.
  • Git builds and direct CLI publishes produce the same bundle digest for the same framework output and target context.
  • Dependency receipts prove whether a configuration change rebuilds content, rebinds paths, or changes activation only; binding never invokes content parsers.
  • Zero bundles cannot be replayed to a different Space or admitted by a Runtime without executeZero.
  • A crash before commit leaves no reachable version; a crash after Runtime commit resumes from the same durable admission receipt without rebuilding.
  • Lost responses after binding, admission, and activation independently replay their exact receipts without repeating prior effects.
  • A worker that loses its delivery claim cannot create or dispatch the next phase receipt; exact already-accepted replay remains safe.
  • Context expiry before first effect fails; expiry after an accepted exact effect does not strand its durable retry.
  • Runtime relocation between context, binding, and admission either rebinds under a new phase epoch or fails without mutation.
  • Out-of-order competing activations and crash injection after every activation subwrite serve either the old or new complete generation, never a mixed projection.
  • Same version/same digest returns the original admission receipt; same version/different digest fails with a hard conflict.
  • Multi-version import resumes after a crash following each individual version admission and moves no channel prematurely.
  • Zero restart, migration, rotation, revocation, and relocation work with no secret value in the public bundle or durable public receipt.
  • Response loss after each Zero migration forward-completes from exact database/migration proof; activation cannot precede the terminal migration receipt.
  • A four-digit test secret yields no bundle, API, receipt, log, or cache value that can verify offline guesses.
  • Hostile Builder inputs covering memory growth, output explosion, expensive parsing, panic/trap, cache poisoning, and filesystem/network access stay inside sandbox quotas and cannot terminate a durable worker.
  • Production proof includes exact revision, bundle digest, Runtime revision, ready version, route pointer, and public HTTP response—not deployment success alone.

12. Explicit non-goals

  • No visual editor or WordPress admin replacement.
  • No PHP/Twig/Liquid second template language.
  • No requirement to execute arbitrary WordPress plugins.
  • No automatic upload of source when a local build fails.
  • No claim that a Zero-capable runtime contains no Rust process.
  • No reuse of Spacefast export archives as the public single-version build format.

13. Adversarial review record

Three independent reviews challenged the first draft. The blocking findings below were accepted and changed the architecture; none were waived.

Review Finding Disposition
Architecture · P0 One receipt was frozen before the binding artifact existed. Replaced with monotonic binding, admission, activation, and public-proof phase receipts.
Architecture · P0 A write lock was incorrectly treated as crash-atomic route activation. Added immutable activation records, derived projections, expected-generation CAS, and pointer-last activation.
Architecture · P1 Version ID alone was insufficient recovery proof; config-only and import were underspecified. Added exact observed Runtime identity, Builder dependency classes, and per-version resumable import receipts.
Security · P0 A trusted Builder consuming secrets could still exfiltrate them. Builder is now secret-blind; encrypted version-bound Runtime handles supply Zero values at execution.
Security · P0/P1 Hashes and public health were treated as stronger authority than they provide. Added signed profile-specific Runtime releases, separate artifact keys, digest-bound JWTs, security epochs, and authenticated capability state.
Security · P2 “Reuse import checks” risked inheriting permissive legacy PHP parsing and weak budgets. Specified a strict language-neutral parser, typed cache writers, fuzzing, and bounded resource budgets.
Product · P0 The existing embedded WASI artifact cannot yet execute a full site build. Chose and gated a full static build_bundle WASI operation with sandboxed preopens.
Product · P0 Proposed commands conflicted with existing build/remote/prebuilt semantics. Kept the whole app-build → artifact-compile pipeline, --prebuilt, --remote, and bundle auto-detection.
Product · P0 Markdown, block-theme compatibility, and Spacefast convenience publishing were overstated or omitted. Added the Markdown graduation phase, an honest compatibility matrix, same-Builder dev mode, and preserved /v1/publish.
Architecture closure · P0 Portable publishes skipped context consumption; stale workers and secret staging lacked exact phase fences. Added universal artifact acceptance, delivery-claim CAS on every phase, and idempotent Runtime secret staging.
Architecture closure · P0 Zero migrations were an irreversible effect hidden between secret staging and activation. Added a fenced migration phase with plan/database identity, per-migration receipts, response-loss recovery, and activation dependency.
Security closure · P1 Secret value digests were offline guessing oracles and hosted Builder isolation was optional. Removed value digests from external boundaries and required ephemeral quota-bounded tenant sandboxes.
Product closure · P0/P1 Cloud context preceded portable build; provenance polluted identity; names/output/dev behavior collided. Made build offline-first, separated provenance, defined stattic/sf and their configs, moved output outside inputs, and moved Pages preview to sf pages dev.

14. Final definition of done

A regular user can install the Spacefast/Stattic CLI, publish Markdown and Gutenberg files with a documented supported-block/theme contract, and serve the result from a PHP-only Stattic Runtime. Spacefast adds policy, target binding, Zero, durable activation, and hosting without changing the content compiler or inventing a second publish artifact.

Evidence basis: merged Rust finalizer architecture, current CLI WASI packaging, current control-plane version lifecycle and durable receipts, Runtime import/admission safety, and current Zero target-rebind behavior. This plan intentionally treats the finalizer merge as historical baseline.
